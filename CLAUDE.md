# Project: Ticket to Taitoka (LAN, Online & Pass-and-Play Tabletop Web App)

> **Setting the game up for a player?** Follow "Setup instructions for Claude" in `README.md` (macOS: `bash desktop/setup-mac.sh`; Windows: `powershell -ExecutionPolicy Bypass -File desktop\setup-windows.ps1`). They install Node if needed, run `npm install`, and put a **Ticket to Taitoka** icon on the Desktop.

## Tech Stack & Architecture
- **Monorepo**: `npm` workspaces with `/packages/shared` (rules, types, map JSON), `/packages/server` (Node + `boardgame.io`), and `/packages/client` (React + Vite + TypeScript + Tailwind CSS).
- **Library Docs**: Use `context7` to verify exact APIs for `boardgame.io`, `graphology`, and Tailwind CSS.
- **Board Rendering**: Scalable interactive `<svg>` map with vector tracks, curved/offset double routes, individual clickable train car slots, and city nodes.
- **Graph Engine**: Use `graphology` in `/packages/shared` for ticket completion verification and edge-disjoint longest continuous trail calculation (permitting loops/cycles without reusing individual train pieces)[cite: 4].

## Core Game Rules & State Machine Specifications (`@rules.pdf`)
1. **Setup**: 
   - Each player starts with **50** train cars (house rule; the rulebook says 45)[cite: 2].
   - **House rule: 7 card colours** (purple removed): 14 of each colour + 14 locomotives = 112 train cards.
   - Deal **4 Train Car cards** to each player[cite: 2].
   - Turn 5 Train Car cards face-up in the market pool; place the rest as a draw deck[cite: 2].
   - Deal **3 Destination Tickets** to each player; each must keep at least 2 (may keep all 3), returning unkept tickets to the bottom of the deck[cite: 2].
2. **Turn Actions (Pick 1 of 3)**:
   - **Draw Train Car Cards**: Draw 2 cards total. Face-up locomotive rule: taking 1 face-up locomotive ends the draw phase immediately (cannot draw a second card); if a replacement card is a locomotive, it cannot be taken. If 3 of the 5 face-up cards are locomotives, all 5 are immediately discarded and replaced[cite: 3]. Blind draws from the deck count as 1 card even if a locomotive is drawn[cite: 3]. If deck and discards are completely empty, drawing train cards is disabled[cite: 3].
   - **Claim a Route**: Play a set of matching colored cards equal to the route length (or gray routes using any single color plus optional locomotives)[cite: 3]. Score points immediately based on the official table: 
     - 1 length = 1 pt[cite: 4]
     - 2 length = 2 pts[cite: 4]
     - 3 length = 4 pts[cite: 4]
     - 4 length = 7 pts[cite: 4]
     - 5 length = 10 pts[cite: 4]
     - 6 length = 15 pts[cite: 4]
   - **Draw Destination Tickets**: Draw 3 tickets from the top of the deck; must keep at least 1 (up to all 3)[cite: 3, 4].
3. **Double-Routes (house rule)**: 
   - At every player count both tracks of a double route are usable, but one player may own only one of the two. (The rulebook closes the second track in 2–3 player games[cite: 3]; this game uses the house rule.)
4. **Game End & Final Scoring**:
   - Triggered when any player's train stock drops to **0, 1, or 2 trains** at the end of their turn[cite: 4]. Every player (including the trigger player) gets **one final turn**[cite: 4].
   - Final scoring adds completed ticket values and subtracts uncompleted ticket values[cite: 4].
   - Longest Continuous Path bonus awards **10 points** (ties split the bonus)[cite: 4].
   - Tie-breakers: 1) Most completed Destination Tickets, 2) Longest Continuous Path card[cite: 4].

## Editions and Skins (USA / China / Europe / Singapore, chosen at runtime)
- **One build, one server.** `npm run play` builds the client once and starts the server; the player picks the edition in the browser. There are no per-edition build modes, `.env.*` files or `play:usa|china|europe|singapore` scripts.
- An **edition** (`packages/shared/src/editions.ts`: `EDITIONS`, `EDITION_IDS`, `isEditionId`, `editionFor`) fixes three things together: the map, the skin (game name) and the theme. `usa` = Taitoka skin, USA map, `vintage` theme ("Ticket to Taitoka"); `china` = Beijing skin, China map, `hsr` theme ("Ticket to Beijing"); `europe` = Europa skin, Europe map, `rail` theme ("Ticket to Europa"); `singapore` = Singapore skin, SG map, `merlion` theme ("Ticket to Singapore"; the hub is named Marina Bay via `skin.hubName`). Only these four are offered.
- A **skin** (`packages/shared/src/skins.ts`) changes only the game name (= hub city `BOB`'s name, unless `hubName` is set).
- Client: `packages/client/src/edition.ts` is imported first in `main.tsx`. It resolves the edition (`?edition=` in the URL, else `localStorage` `ttb.edition`, else `usa`), sets `globalThis.__TTB_EDITION__`, `<html data-theme>` and the tab title, and exports `EDITION`. `setEdition(id)` saves the choice and reloads, because many modules read the map and theme once when they load. `/` is the edition picker (`EditionPicker`): one Ticket to Taitoka series card (`series-card`, art and styles in `screens/seriesArt.tsx` + `series.css`) that opens a blurred-backdrop map chooser (`map-chooser`) with one small card per edition (`pick-<id>`); a click anywhere that is not a map card, or Escape, closes it (e2e: `openMaps()` in `e2e/helpers.ts`). `/menu` is the start menu, and `EditionSwitcher` (via `Frame edition`) switches edition on the menu, local setup and waiting room.
- Client code must use `cityName(id)`, `SKIN` and `GAME_TITLE` from `packages/client/src/lib/skin.ts`, never `CITY_BY_ID[id].name` or a literal game name; `skin.test.ts` enforces this.

## Bots (LAN/online waiting room)
- The host adds Easy / Medium / Hard bots to open seats (`/api/bots/add`, `/api/bots/remove`, host checked by seat-0 credentials). The seat's `data.bot` holds the level.
- Brain: `packages/shared/src/bot/`, a pure `chooseBotMove(view, ctx, me, level, rng)`. Strategies are in `levels/`, planning in `plan.ts`, and opponent guessing in `opponents.ts`. `legalize()` turns any illegal choice into a legal one, so a bot never stalls the game.
- Bots play fair: they decide only from their own `playerView`. `test/botRunner.ts` enforces this.
- Server: `packages/server/src/bots.ts` connects one socket client per bot to the server. Bots follow the group into the game and back into the next waiting room. Each action waits about 1.1 s, and the first action of a turn about 2.1 s (`turnLeadMs`, 2100/1100 x the delay) so the turn banner is over first; `TTB_BOT_DELAY` overrides the delay and the lead scales with it (e2e uses 50 ms).
- Tests: `bot*.test.ts` and `fuzz.bots*.test.ts`, plus `bot.strength.test.ts`, which checks that Hard > Medium > Easy.

## Chat
- LAN, online and pass-and-play: boardgame.io's chat relay (`client.sendChatMessage`, `client.chatMessages`), passed from `screens/Lan.tsx` to `GameScreen` as `chat`. Received payloads are untrusted: always read them through `readChat()` in `packages/client/src/lib/chat.ts` (text capped, emotes from a fixed list). Messages are not stored, so a reload starts with an empty chat.

## Maps (USA / China / Europe / Singapore)
- **Runtime maps, one process.** All maps are loaded; the active map is a live binding that `useMap(id)` / `withMap(id, fn)` (`packages/shared/src/map/index.ts`) switch. Every game records its own map in `G.mapId` (set in `setup` from `setupData.map`, default `DEFAULT_MAP_ID`). `BobolandGame` wraps every hook (setup, moves, `playerView`, phases, `endIf`...) in `withMap(G.mapId, ...)`, so one server runs games on different maps at once. Code that runs outside the game hooks (bots, `legalActions`, `chooseBotMove`) uses `withGameMap(G, fn)` / `mapOfGame(G)`. `setupData` is validated (an unknown map is rejected).
- `DEFAULT_MAP_ID` (`map/index.ts`, from `activeMapId()` in `map/active.ts`) is fixed when the code loads: in the browser it follows the edition (`globalThis.__TTB_EDITION__`, set by `edition.ts` before the map code loads); on the server and in tests it is `TTB_MAP`. The server (`packages/server/src/map.ts` `defaultMap`) takes `--map=`, else `TTB_MAP`, else `usa`; it only decides which map a match gets when `setupData` names none. Clients always send `setupData: { map }`.
- Pass-and-play: `lib/setupGame.ts` `gameOnMap(game, map)` passes the map into `setup` (boardgame.io's local Client cannot pass `setupData`). LAN: `startLanMatch` sends `setupData: { map }` to `playAgain`, using the room's edition (seat 0 data) when known (`mapForRoom`), else this page's edition.
- Map data: `map/usa/` (cities, routes with optional `curve`, tickets, Albers projection, generated geography), `map/china/` and `map/europe/` (37 cities, 83 links / 94 routes, 42 tickets; London + Edinburgh only in Britain; the long 5-6 routes sit mostly in the North Sea / Scandinavia / Baltic). Geometry (lanes, car slots, curves, crowded-city insets) is in `map/model.ts`; client code gets cars from `carRects()` and draws them with `CarBox` so curved cars bend.
- USA map rules are tests in `packages/shared/test/usa-map.test.ts` (no colour 3+ times into a city; exactly Nashville, Atlanta, Pittsburgh have one colour twice; equal cars per colour; no city easy to cut off; no crossings or touching cars). `fuzz.usa.test.ts` plays 500 games on it. China: `china-map.test.ts`, `fuzz.china.test.ts`. Europe: `europe*.test.ts`. `editions.test.ts` covers runtime switching and `G.mapId`.

## Frontline (separate 2-player game, not an edition)
- A hidden-piece strategy game (10x10, lakes, 40 pieces a side) on the same server, lobby, chat relay and pass-and-play curtain. Never use the trademarked name. It is not in `EDITIONS`; the `/` picker has a separate card that opens `/frontline`.
- Rules (pure TS, no maps): `packages/shared/src/frontline/` (`pieces.ts` army table, `board.ts` geometry, `rules.ts` combat/moves/two-square rule/outcome/setup validation, `view.ts` the only rank filter, `game.ts` `FrontlineGame`, game name `frontline`). Registered next to `BobolandGame` in `packages/server/src/serve.ts`.
- **Hidden-info rule:** `G` always holds every rank; clients only get `viewFor` (playerView): enemy pieces have no `rank` key until revealed, the enemy army is absent during setup, everything is shown after the game. Every move is `client: false`; `submitSetup` is also `redact: true` so its placement never reaches the opponent's log. Piece ids come from the starting square, never the rank.
- Lobby: no waiting room. The host creates a 2-seat `frontline` match and the joiner takes seat 1 (`/frontline/join/:id`); rematch is `playAgain` with 2 seats. Client: `packages/client/src/frontline/`. `Local()` keeps one master per game object, so each local match needs a fresh `{ ...FrontlineGame }`.
- Tests: `npx vitest run packages/shared/test/frontline packages/shared/test/fuzz.frontline.test.ts` (rules, Local() no-leak test incl. reconnect, 500-game fuzz) and `npx playwright test e2e/frontline.spec.ts` after `npm run build`.
- Extra rules: a simplified more-squares rule (`G.chase`: a chaser may not recreate a position seen during an unbroken chase of one fleeing piece; yields like the two-square rule). `G.fallen` lists pieces lost in combat. Optional per-turn limit: setupData `{ turnSeconds }`, the waiting player's client calls `claimTimeout` (checked on the server clock).
- **Armies** (`pieces.ts` `ARMIES`, `G.army`, setupData `{ army }`, briefing move `setArmy`, host only): `classic` (40 pieces, 4 setup rows) or `spotter` (30 pieces, 3 rows: 1 Marshal, 1 General, 2 Colonels, 2 Majors, 3 Captains, 3 Lieutenants, 3 Sergeants, 4 Engineers, 4 Scouts, 2 Spotters, 1 Operative, 3 Mines, 1 Command Post). The Spotter is rank `'P'` (strength 1.5: beats the Operative both ways, loses to everything else, ties with a Spotter); its tile shows "1" and the Operative "S" in that army (`badgeOf`, `ArmyContext` in `Tile.tsx`). Instead of moving, a Spotter may `spot(from, at, guess)` an orthogonally adjacent enemy: right = the target is removed (mines and the command post too, which wins), the Spotter stays; wrong = the target stays hidden and the guess is added to the public `G.ruledOut[pieceId]` (never repeatable). The Spotter is revealed either way. `G.lastSpot` never holds a missed target's rank. A spot clears the streak and chase. Rules: `spotTargets`, `spotGuesses`, `isLegalSpot`, `applySpot`; bot `chooseBotAction` (spots by the odds from its own view). Client: picker `SpotPicker` (with "Attack instead"), cyan optics marks and the spot animation in `spot.css` (timing `SPOT_T` in `fx.ts`), Spotter presets `SPOTTER_PRESETS`, saved layouts kept per army. Tests: `frontline.spotter.test.ts`, the Spotter fuzz in `fuzz.frontline.test.ts`, `e2e/frontline-spotter.spec.ts`.
- Phases: `briefing` (start; empty board; seat 0 sets `setTurnLimit` and calls `begin`; names/limit are edited on the game screen, no pre-game pages) -> `setup` (each side deploys from a tray, presets in `client/src/frontline/presets.ts`; Confirm appears only for a full army) -> `play` (`G.startedAt` drives the elapsed clock). Leave = in-page confirm, resigns during setup/play, then back to `/frontline`.
- Bot: `frontline/bot.ts` (`botPlacement`, `chooseBotMove` from the bot's own view), played in the browser by `/frontline/bot`; no server bots. Spectators: `/frontline/watch/:id` (no playerID, so no ranks).
- Look and animation (client): tiles are `Tile.tsx` (number, `art.tsx` illustration, name; an unseen enemy tile is only the army crest, with no text). `Board.tsx` draws the tactical map (contours, lakes, A-J / 1-10 rim in real coordinates) and plays slides, the attack lunge, the target reticle and reveal flips. An attack plays the `Duel.tsx` cinematic over the board; all timing is in `fx.ts` (`COMBAT_T`, `fxFor`, read by CSS as `--t-*`). During a duel the board shows the pre-attack position, input is blocked, and the banner/result wait until it ends. The computer moves `botDelay()` = the last move's animation + 1.2 s. Pass-and-play keeps the mover's screen up until their move has played, then the curtain falls. Never use the class name `hidden` for custom CSS (Tailwind's utility hides it).
- Deferred: replays, ranking, server-side bots, a draw-offer button.

## Egyptian War (separate 2-5 player real-time game, not an edition)
- A card-slapping game: flip in turn, J/Q/K/A challenge the next player (1/2/3/4 tries), anyone slaps a pattern to take the pile, win all 52 cards. Spec with every open-point decision: `docs/egyptian/SPEC.md`; build checklist: `docs/egyptian/PLAN.md`. Not in `EDITIONS`; the `/` picker has an `egyptian-card` that opens `/egyptian`.
- Rules (pure TS, explicit `now` everywhere): `packages/shared/src/egyptian/` (`cards.ts` card = 0..51; `slapRules.ts` = the 14-rule catalogue as data, each with a detector returning the matching indices, `matchSlap` in catalogue order; `timing.ts` = every server timing (`TIMING`, `QUICK_TIMING`); `rules.ts` = `newGame`/`ready`/`flip`/`slap`/`tick`/`leave`, each returns an error string or applies; `view.ts`; `game.ts` `EgyptianGame`, game name `egyptian`, setupData `{ rules, waiting, quick }`). Registered next to Fleet in `packages/server/src/serve.ts`.
- House calls: 1 s grace before a challenge winner collects (slaps still count); a false slap burns 1 card face down under the pile and locks that player's slaps out for 1 s; a player with no cards gets one slap-in per round; min 400 ms between flips; a slap also counts on the pile from before a flip up to 200 ms old; a slap stamped with an older round is ignored free; idle auto-flip after 15 s; `leave` puts your cards under the pile.
- **Real time in boardgame.io:** every seat is always active (`ActivePlayers.ALL`), the game keeps its own turn (`G.turn`), and every move is `client: false` and `ignoreStaleStateID: true` (otherwise most slaps would be refused as stale); each rule re-checks its preconditions. No server timers: timed events (deal start, grace, collect, auto-flip) are the `tick` move, checked on the server clock; seated clients call it from `useTimers` (`egyptian/controls.ts`, staggered per seat, retried every 150 ms).
- **Hidden-info rule:** `G` holds every card; `viewFor` gives everyone (players and spectators alike) stack `counts` and `burnedCount` only, never a stack or a burned card, even to the owner or after the game. The `falseSlap` event carries no card.
- Client: `packages/client/src/egyptian/` (CSS prefix `egw-`, never `hidden`). Routes `/egyptian` (menu), `/egyptian/local` (2 players, one keyboard: P1 left Q flip / W slap, P2 right ] flip / [ slap; `?seed=` fixes the deal), `/egyptian/host`, `/egyptian/wait/:id` (5-seat waiting room: colours, the host's rule checklist shown live, Start with 2+), `/egyptian/join/:id`, `/egyptian/play/:id` (online keys F / Space), `/egyptian/watch/:id`, `/egyptian/deck` (QA gallery of all 52 faces + back). `EgwScreen` serves every mode; `table/Table.tsx` draws the oval (viewer at the bottom, play clockwise = next player on the left, `seating.ts`), the fanned pile and every animation, driven by new log events (`table/useTableFx.ts`). Key bindings (`keys.ts`, by `KeyboardEvent.code`, saved in `egw.keys`, editable in `KeySettings`, never captured in inputs, repeats ignored). Waiting-room seat data in `roomData.ts` (colour; seat 0 also `rules`); lobby calls in `lobby.ts`; rematch = host opens the next waiting room and everyone rejoins with their seat number.
- **Deck system:** card art comes only from the active `DeckSkin` (`egyptian/decks/`: `Face`, `Back`, `Defs`, `--deck-*` accent tokens, music track) through `CardView`; the table is deck-neutral. A second deck is a new folder plus one line in `DECKS`. The Egyptian deck (`decks/egyptian/`) is inline SVG: papyrus stock, gold double border, lotus frieze, classic red/black suits with real pip layouts, four houses (Night, Nile, Sun, Delta), 12 double-ended court figures (`courts.tsx` + `figure.tsx`), 4 ornate Aces, a rotationally symmetric lapis back.
- Timings: server pauses in `shared/src/egyptian/timing.ts`; animations in `egyptian/fx.ts` (Full / Fast / Off in `egw.fx`, reduced motion = Fast; `fx.test.ts`-style check in `foundations.test.ts` that Full fits the pauses). `egw.e2e` = '1' turns animations off and asks the server for `quick` pauses.
- Sound `egyptian/sound.ts`; music `lib/songEgyptian.ts` (Hijaz mode, frame drum, lute, reed flute) on its own bus in `lib/music.ts`. Party: members take free waiting-room seats and follow into the game, anyone without a seat watches (`partyRules.ts`). Chat online only (`readChat`).
- Tests: `npx vitest run packages/shared/test/egyptian* packages/shared/test/fuzz.egyptian.test.ts packages/client/src/egyptian` (catalogue, rules, slaps, Local() no-leak incl. reconnect, 500 fuzz games per player count 2-5 with capped games reported, client logic, deck, sounds) and `npx playwright test e2e/egyptian.spec.ts` after `npm run build`.

## Warfront (separate 2-6 player territory-conquest game, not an edition)
- Modern-warfare conquest following the classic territory-conquest board game's rules. Never write that game's trademarked name. Spec: `docs/warfront/SPEC.md`; build checklist: `docs/warfront/PLAN.md`. Not in `EDITIONS`; the `/` picker shows `WarfrontCard` (`warfront/PickerCard.tsx`, one line in `EditionPicker.tsx`), which opens `/warfront`.
- Rules (pure TS): `packages/shared/src/warfront/`.
  - `rules.ts` `act()` validates and applies one action: claim, place, placeNeutral, autoPlace, trade, deploy, attack, blitz, occupy, endAttack, fortify, endTurn. Also `resign`. Seeded rng.
  - `cards.ts`: deck, sets, trade values 4 6 8 10 12 15 +5, missions.
  - `view.ts` `viewFor`: the only hidden-info filter. Others' cards are counts, there is no deck, and missions show only your own until the game ends.
  - `bot.ts` `chooseWarAction`: Easy, Medium and Hard, from the bot's own view, always legal.
  - `game.ts` `WarfrontGame`: game name `warfront`, setupData `{ mode, autoDeploy, factions }`. A single `act` move and `resign`, both `client: false`, with `ActivePlayers.ALL`; the engine checks whose turn it is.
  - Registered in `serve.ts` next to `FleetGame`.
- Map (original division of real geography): `mapData.ts` (42 territories, 6 continents, coastlines, inland seas, `SEA_LINKS`). `geometry.ts` uses a Miller projection (1600 x 752); territory shapes are Voronoi cells of the label points clipped to the coastlines. Land borders are derived from shared cell edges on land, so moving a label point changes borders. `warfront.rules.test.ts` pins the border count (77).
- Server bots for online rooms: `packages/server/src/warfrontBots.ts` (`/api/warfront/bots/add|remove`, host checked by seat-0 credentials). It follows the Ticket bots' pattern: bots follow the group from the war room into the battle and into the next war room. Pace comes from `TTB_BOT_DELAY`.
- Client: `packages/client/src/warfront/` (CSS prefix `wf-`; `.warfront` is `isolation: isolate`).
  - Routes: `/warfront` (desk menu: map = muster sheet, phone = online, binder = Field Manual), `/warfront/bot|local?s=` (`Local.tsx`: a Local() master, one client per seat, computer seats act from their own view; pass and play shows a leather map-case `Curtain`), `/warfront/host|join|wait|play|watch/:id` (`Lan.tsx` and `lobby.ts`).
  - The war room is the Ticket waiting-room pattern: a 6-seat match, colours in seat data, seat 0 holds the settings, Start calls `playAgain` with the joined count and the factions.
  - Online clients must be created with the real `numPlayers` (`useMatch` reads it from the match first).
  - `WarScreen.tsx`: orders per stage, deploy drafting with undo, dice and dial, intel cards, teleprinter, keyboard shortcuts. `Board.tsx`: the SVG war table. `useZoom.ts`: the viewBox follows the container's shape, so phones pan a full-height map.
  - All timings are in `fx.ts` (Full/Fast/Off in `warfront.fx`; computer pace from `warfront.botMs`; both values are JSON in localStorage).

## Game Modes & LAN Networking
- **LAN Multiplayer**: Bind Vite and `boardgame.io` server to `0.0.0.0`. Display local LAN IP URL + QR code (`qrcode.react`) in the lobby. Use `playerView` to hide draw deck orders and opponents' secret tickets.
- **Pass-and-Play**: Single-device turn-based mode with a privacy curtain between turns.
- **Party**: everyone is in a party (up to 5 real people, never bots). A first visit asks for a name (`NamePrompt`); the `Party` button (top-right of every screen, `components/Party.tsx`) shows one blue dot per person and opens the panel: members, rename, the invite link + QR (`/p/:partyId`), host kick, member leave. Server: in-memory `packages/server/src/party.ts` (`/api/party/*`, members dropped after 25 s silent, host passes on). Client: `lib/party.ts` polls; the host reports its path + edition, members follow via `lib/partyRules.ts` (`followTarget`; local modes and games without a seat show `/party/hold`). The party remembers its waiting room (`room`) while the host moves between maps (bots kept); going to `/` drops it. Hosting/joining never asks for a name; names are edited in the panel or the waiting room. Tests: `party.test.ts`, `partyRules.test.ts`, e2e `party.spec.ts`.
- **Lobby (LAN/online)**: hosting creates a 5-seat waiting-room match (no player count). Joiners pick colours there (`data.color` via the Lobby `update` API). Seat 0's `data.edition` is the room's edition: only the host sees an enabled `EditionSwitcher` in the waiting room (`setRoomEdition`), every other screen is locked and follows (`useFollowEdition` reloads into the host's edition; `lib/seatData.ts` merges seat data, since `updatePlayer` replaces `data`). `LanGame` also reloads into the edition of `G.mapId` if it differs. The host's Start calls `playAgain` with the number who joined and `setupData: { map }`; every waiting room sees `nextMatchID` and joins the new match in seat order (`packages/client/src/lib/lobbyRules.ts`, `lib/lobby.ts`).
- **Turn order**: `setup` shuffles all seat ids with boardgame.io's seeded `random.Shuffle` (after the card shuffles) into `G.turnOrder`; the main phase uses it as `playOrder`, so both who starts and who follows whom are random (bots and humans alike). Seat ids, colours and the waiting-room mapping do not change. `finalTurnsDone` reads `G.turnOrder` too.

## Engineering & Testing Standards
- **TDD (`superpowers:test-driven-development`)**: Write failing Vitest unit tests before implementing core rules. Include fuzz tests running 500 simulated games to ensure zero soft-locks.
- **Playwright E2E**: `npm run e2e` builds the client once and runs every spec against the one server (default map `usa`). Specs open `/menu` (or `/menu?edition=china|europe`; `/` is the edition picker) and play on the USA edition unless they pick another. `?seed=e2e1` makes pass-and-play deterministic (Bo first on the USA map; seed `e2e` gives Ana). Specs: pass-and-play, 2-window LAN sync, bots, music, `frontline.spec.ts`, `fleet.spec.ts`, `egyptian.spec.ts`, `warfront.spec.ts`, `china.spec.ts` and `europe.spec.ts` (seed-independent, via `?edition=`), and `editions.spec.ts` (picker, menu switcher, local game on the chosen map, host switches the map in the waiting room and the joiner follows).
- Commands: `npm run dev` (server + Vite), `npm run build`, `npm run play`, `npm run play:online`, `npm run start`, `npm run typecheck`, `npm test`, `npm run e2e`.
